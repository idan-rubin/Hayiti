# Map My Trip

## Start with the owned trip

Use `list_trips` to find the traveler's journal. Reuse its trip ID, dates, home base and ordering rules. Read affected dates with `get_day` before proposing edits. For a new trip, resolve the destination and inclusive dates from the request or authorized itinerary. A home base is optional. For a moving itinerary, use the known daily origin where available. Use each venue's local calendar date and time zone, especially around midnight or a border crossing.

Search the sources the traveler selected. Check linked credit or debit purchase accounts before searching Finances. Search receipts by service date, calendar by event date, photos by capture date. A matching card posting, email arrival, or file upload may fall outside the trip dates. When a source is missing, continue with the others. When sending `sourceChecks`, supply the exact trip `start` and `end` alongside that field and include only sources actually checked. Distinguish disconnected, syncing, failed, partial, no purchase accounts, zero transactions, and transactions with no mappable place. Use the tool's advertised statuses. Report photo and Google Maps access separately when there is no corresponding status field.

## Identify visits and order each day

1. **Identify the branch.** Match the venue, address, local date and type of transaction. Check merchant aliases, transliterations and receipt details. A processor's HQ, an online order and a charge posted days later do not establish a visit. A market, stall and neighboring café may share coordinates. Merge only evidence of the same visit. Preserve a return visit supported by a separate event. Leave an uncertain or remote purchase off the route.
2. **Anchor the sequence.** Preserve the traveler's manually ordered stops, explicit corrections, and “A before B” rules. Use timed evidence of actual presence such as an on-site receipt, a located photo or a pickup/drop-off. A reservation or ticket supplies a scheduled time. Look for attendance evidence. Use a transaction time only when it represents the local purchase, and keep a bank posting time out of the visit's `time` field. Where anchors conflict, explain the conflict and retain the traveler's confirmed sequence.
3. **Look up opening hours when they can resolve the order.** Verify the exact branch, local date, weekday, service in question and exceptions. For a past Friday, look for that Friday's hours, holiday or early-closing notice, and whether late service continued after midnight. Prefer a dated venue notice, archived official timetable or contemporaneous booking. Current regular hours may suggest an order for a past trip but do not verify historical hours. Keep each service window separate when a venue closes and reopens. Treat its opening time as the earliest plausible visit, never as the visit time.
4. **Order only as far as the evidence allows.** Between fixed anchors, if every plausible interval for A ends before any interval for B begins, place A first. For example, a café confirmed open 08:00–14:00 and a bar confirmed open 18:00–23:00 support café before bar. Overlapping windows leave both orders possible. For two date-only purchases at a fictional café (08:00–20:00) and bar (18:00–01:00), both might have taken place during the overlap. The traveler's recollection of a morning coffee favors café first, with no exact time. If the recollection conflicts with posted hours, recheck the branch and schedule before changing the suggestion. Check travel time, then use proximity as a tie-breaker. Preserve existing rank for unresolved ties. Never invent a clock time to make an order stick.
5. **Explain consequential uncertainty.** Identify what the traveler confirmed, what a source actually records, and what you inferred. For a disputed order, give one short reason and the dated hours source when applicable. Ask one focused question if the choice would materially change the route and the evidence cannot settle it. Use opening windows and confidence in the agent's reasoning. Write only fields the connected writer advertises.

## Import photo locations

1. Use the specified photo library. Apple Photos, Google Photos and Google Drive have separate permissions. If the requested library offers a usable signed-in view or integration, use it. Check the full local trip date range across albums. Prefer original EXIF capture time and GPS (including HEIC), or video creation time with offset and embedded coordinates. The library's information panel can distinguish recorded and estimated locations. Count a Live Photo and its motion companion once. Skip items with no usable location.
2. For large batches, run the bundled TypeScript helper with Node 24 or later: `node scripts/group-photo-pins.ts` from the skill directory. Feed it a JSON array on stdin with one `{id,date,time,xy}` per capture (local time and latitude first). It returns groups with the original observations. Use stable opaque asset references. Compare photo-only locations within the same local day to a fixed pin anchor, within 100 metres. Never chain a series of short steps into one distant group. Keep the earliest known capture's coordinates and retain second or millisecond precision in `captureTime` when available. Preserve manual edits across retries. An independently identified nearby venue or a different day's visit can remain distinct.
3. Link to an existing visit only when time, coordinates and place evidence agree. For an unidentified place, use a neutral photo pin and the `photo` source. Leave original images, private links and identifying metadata out unless needed and requested. Report photographs checked, missing GPS and pins added or linked.

## Import Google Pins

Use the authorized Google Maps list, readable shared list or export. Ask for a list link if you cannot access it. Resolve a place to a specific identity and verified coordinates. Google GeoJSON uses longitude first and may use [0, 0] for an unknown location. Send hayiti coordinates in [latitude, longitude] order.

Read existing bookmarks with `list_google_pins`. Use `googlePins` in `add_trip_stops` with a stable opaque ID per Google place. For a bookmark-only import send `stops: []`. Set `savedAt` only for an explicit save date or timestamp. Google Saved lists can omit it, and a Starred places timestamp can record creation **or modification**. An export or file time cannot establish the save date. [Saved collection fields](https://developers.google.com/data-portability/schema-reference/save) · [Starred place fields](https://developers.google.com/data-portability/schema-reference/local_actions)

Prefer the traveler's chosen day. Otherwise assign `date` from a verified save time in the correct local zone. Keep unknown or out-of-range days unassigned. Respect day assignments the traveler changed or cleared. Assigned pins appear on that day, and all pins appear in Whole trip. A bookmark alone never establishes attendance or adds distance. Record an independently confirmed visit using the usual stop evidence.

## Save, route and verify

1. Save the traveler's approved scope to the owned trip with `add_trip_stops`. Give each visit a stable opaque reference per source and supply new visits in the intended order. The writer appends new stops and links matching evidence. After adding them, read `get_day` for the saved IDs, ranks, and current route. Resending rows in another order does not rearrange existing visits.
2. Work out network directions for adjacent stops in the intended order for that day, including its known origin. Match a taxi receipt to both ride endpoints and request driving directions for that leg. Use pedestrian directions for plausible walks, including long walks between nearby cities. A taxi fare elsewhere that day does not turn another leg into a ride. For a distant transfer, check elapsed time and transport evidence. Leave an unresolved or unsupported flight, rail or ferry leg unclassified and preserve its existing display. The trip overview draws the individual days without inventing overnight transfers.
3. Retain valid geometry for unchanged ordered endpoints and mode. Recheck the pairs touching an inserted, moved or deleted stop. Request directions with just the endpoints and mode. Reuse results for repeated ordered pairs. Prepare each route's `a` and `b` IDs, `type`, ordered `line` coordinates and network distance `m` for `set_day_routes`. Use `same` for coincident stops and `gap` for an explicitly requested break. Missing coordinates or an unavailable route leave the existing fallback in place. A directions service's chosen path is an estimate of the journey. For a portable journal, supply the matching trip's `hayiti-routes/1` package to import.
4. For a day keeping its order, write only the affected legs with `set_day_routes`. When a day needs reordering, check the connected `set_day_routes` schema for `order`. If available, send `{tripId, date, order: {previous, next}, routes}` in one call. Build `previous` from the saved sequence returned by `get_day`. Include every visit, pickup and drop-off ID exactly once. Exclude home and daily origins, uncertain and remote stops, and Google Pins. Use the same IDs in the proposed order for `next`. Keep matched taxi endpoints adjacent in pickup-to-drop-off order. Provide network geometry for adjacent pairs in `next`. Use an empty `routes` array for order only. The same order object belongs on a portable route package's day. On a stale-order error or uncertain write result, read the day again and reconcile any manual edits before retrying. If the host lacks `order`, use the journal's ordering controls within authorization or report the proposed changes as pending. Never claim an unsaved reorder.
5. Re-read each affected day and, for bookmark imports, `list_google_pins`. Check existing edits, source references, counts, assigned days, order, route modes, vertex counts and walking totals. Report material uncertainties or missing segments with one concrete day. Return the existing private journal link. Daily view is the default. Whole trip shows all days. Streets, satellite and terrain change the background in either view. Create a shared snapshot only when requested. Keep private data out of public examples and pull requests.
